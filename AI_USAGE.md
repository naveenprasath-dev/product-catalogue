# AI usage

How I used AI to build this PoC. This is the summary; the raw notes (every key prompt, decision and
AI mistake, in order) are in [AI_LOG.md](AI_LOG.md), and development problems are in
[ISSUES.md](ISSUES.md).

## 1. Tools
- **Claude Code** with **Claude Opus 5.5**, for planning, code, tests, docs and reviews.
- **Plugins:** **Playwright** (driving the running app for screenshots, QA and layout measurements).
  The `code-review` plugin was installed but not used in this build; reviews were done by agents,
  the QA agent, rule-audit greps and reading the diffs.
- **Laravel Boost MCP** (`laravel/boost`, dev dependency only): version-matched Laravel docs search,
  routes, DB schema, config and logs, run inside the api container. Never installed in production.
  Why I kept it: [DECISIONS.md → Laravel Boost](DECISIONS.md#laravel-boost-laravelboost-dev-dependency-only).

## 2. How I worked with the AI
- **Rules first.** [CLAUDE.md](CLAUDE.md) holds the non-negotiable rules (the client never calls Fake
  Store, the API reads Postgres only, one boundary each for product source, mail and API URL, tests
  before "done"). It is short and always loaded.
- **Project skills** (`.claude/skills/`, 15 of them, plus 3 generated by Laravel Boost in
  `api/.claude/skills/`). *Task skills* give step-by-step recipes with a "done when" check
  (`api-endpoint`, `product-source`, `web-page`, `admin-page`, `catalogue-data`, `run-checks`,
  `pr-ready`, `git-workflow`, `ai-log`, `dev-issues`). *Convention skills* give the house style for
  each side (`laravel-backend`, `laravel-database`, `laravel-testing`, `react-frontend`,
  `react-testing`), so parallel agents write code the same way. Why:
  [DECISIONS.md → project skills](DECISIONS.md#why-i-added-claude-code-project-skills-claudeskills).
- **Contract first, then parallel agents with strict file ownership.** The API contract went into
  PLAN.md before any code. Then separate agents ran at the same time: backend, frontend, admin,
  docs/README, QA, commits, issues, setup, and this logs/decisions agent. Each owned its own files.
  The main session acted as the coordinator: it relayed contracts and "foundation ready" signals
  between agents and was the only one to touch git. See
  [DECISIONS.md → AI workflow decisions](DECISIONS.md#ai-workflow-decisions).
- **Plans before big features.** The admin panel was planned in [ADMIN_PLAN.md](ADMIN_PLAN.md) with
  nine open questions; I answered them before any code was written.
- **A separate QA agent** tested the admin panel and every login path from the outside before the PR.
- **Small commits** grouped by area, made by a commit agent following the `git-workflow` skill after
  `pr-ready` (rule audit, secrets scan, docs in sync). `main` holds no code; everything is on
  `feature/catalogue-poc` and goes in through the PR.
- **Two logs:** AI_LOG.md (how the AI was used) and ISSUES.md via `/dev-issues` (symptom → cause →
  fix → prevention for build, environment and test problems).

## 3. Key decisions I made
- Laravel instead of the Node backend the AI first proposed.
- Two (later three) parallel build agents, with the API contract written first.
- Convention skills on top of task skills, so both sides follow one style.
- Added login/logout for customers and an `/admin` panel on Laravel's React starter kit, both left
  out of the first plan. I answered ADMIN_PLAN's nine questions (e.g. one shared session, password
  reset CLI-only, re-send failed enquiries in the MVP).
- `main` empty; all work on `feature/catalogue-poc` in a public repo.
- Redesigned the shop to look like a modern e-commerce site, with no invented store claims.
- Kept Laravel Boost; approved four new CLAUDE.md rules (cookie auth only, user id from the session,
  JSON errors only for `api/*`, admin toasts for domain errors).
- Configurable currencies, converted on the backend, with live rates from an open-source API
  (Frankfurter, no key).
- A QA agent before the PR, a separate issues log, a one-command setup script with demo data, and a
  separate agent to keep these logs current.

## 4. Where the AI got it wrong, and how it was caught
Full list in [AI_LOG.md](AI_LOG.md#where-the-ai-got-something-wrong--i-corrected-it).
- **Scope gap:** the plan quietly cut user login and never flagged it. *I* caught it on the running app.
- **Tests wiped the dev database** (`<env force>` lost to container env vars), and **`artisan serve`
  dropped env vars** so the API ran on sqlite. *Agents* caught both; fixed and logged (ISSUES #3, #4).
- **Out-of-date skill:** `react-testing` used an MSW v2 option that MSW 3 silently ignores. Caught
  by the frontend agent; the skill was fixed.
- **Missing `.gitignore`**: the root `.env` would have been committed. Caught by the README agent.
- **"Fixed" without checking:** an agent reported the mobile header fixed, but the 375px screenshot
  still overlapped. Caught in my review of the screenshot; now verified with bounding-box measurements.
- **Security bugs** found by the QA agent: a login timing leak that showed which emails are admins,
  and personal data visible via Back after logout (ISSUES #17, #18). Fixed with tests.
- **Coordination slip:** a "foundation ready" message was relayed late, and the admin agent edited
  two resource files owned by the backend agent. Reviewed and kept.
- **Lost evidence:** a test failed once and was rerun before its name was saved (ISSUES #25, open).
- **Stale screenshots:** admin screenshots still show the old Laravel logo (noted in the README).

## 5. How I verified the AI's output
- **Tests in containers** (`docker compose exec api php artisan test`, `docker compose exec web npm
  test`), on a separate `catalogue_test` database, with `Http::fake()`/`Mail::fake()` and MSW (no
  real network). At the last full run: **235 API tests and 69 web tests passing**, plus Pint,
  ESLint, `tsc` and the admin's `vp check`.
- **Playwright** on the real app: screenshots of every page at desktop and phone sizes, and
  bounding-box overlap checks at 320/375/414px for the mobile header.
- **QA report** ([docs/qa/ADMIN_QA.md](docs/qa/ADMIN_QA.md)): 71 cases, 7 bugs found, all 7 fixed with
  regression tests.
- **Rule audits** with the `pr-ready` skill before commits: CLAUDE.md rules, secrets scan, docs in sync.
- **Fresh runs** with `docker compose down -v && docker compose up --build`, to check that a reviewer's
  first start works.
- **Reading the diffs myself** before each commit (staged diff + secrets scan per the `git-workflow` skill).

## 7. What I'd do differently next time
- **Save failing output before rerunning** (`php artisan test 2>&1 | tee …`), so a flaky failure
  can be traced.
- **Freeze time in time-sensitive tests** (`travelTo()`), e.g. the 5-minute re-send window and
  throttle windows.
- **Check UI claims by measuring**: a "fixed" layout needs a screenshot or a bounding-box check of
  the exact element, not "no horizontal overflow".
- **Relay agent signals straight away**, and have agents stop rather than edit files they don't own.
- **Ask the AI to list what the plan leaves out** at the start, so gaps like login are a decision,
  not something I find later.
- **Retake screenshots as part of any visual change**, so evidence doesn't go stale.
